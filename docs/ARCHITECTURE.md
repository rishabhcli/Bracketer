# Bracketer Architecture

Bracketer is a native SwiftUI camera app built around small deterministic contracts where hardware allows it, and explicit simulator seams where hardware does not.

## Capture

`CameraController` owns the AVFoundation session, permission requests, lens selection, bracket capture, Photos writes, runtime diagnostics, and the transition into review. It keeps live camera behavior separate from UI-test simulation through launch arguments such as `-ui-testing-disable-camera-startup` and `-ui-testing-simulated-camera`.

Capture state is represented by `BracketSequenceState`, so UI can show preparing, capturing, saving, completed, failed, cancelled, and timeout phases without guessing from booleans alone. Live Photos writes report `PhotoSaveResult` values with filename, optional asset identifier, duration, and success state.

## Planning

`BracketPlan` and `BracketSequenceState` are the pure domain layer for exposure sequences. They normalize EV step and shot-count inputs, generate symmetric EV offsets around the requested exposure compensation, label every planned shot, and explain any normalization. Unit tests cover 3, 5, and 7-shot plans plus unsupported inputs.

## Settings

`SettingsStore` persists camera preferences in `UserDefaults` and normalizes values on load and write. The UI binds through `ModernContentView`, `ModernProControls`, and `ModernSettingsPanel`, while tests can reset settings with `-ui-testing-reset-settings` for deterministic state.

## Review

`BracketReviewSequence` is the shared review model for simulated and Photos-backed review. It tracks selected shot, best exposure, missing planned assets, loaded resource type, loaded metadata, RAW/processed representation choice, deletion, and clamping. `SimulatedBracketReview` gives UI tests a fixed bracket review without Photos writes; `ImageViewer` uses the same contract for real Photos assets. Both review surfaces can render `BracketReviewNarrativeCard` when a manifest exists, keeping generated or deterministic review explanations anchored to the same manifest state as export.

## Manifests

`BracketManifest` is the JSON-ready bracket group snapshot. It combines the resolved `BracketPlan` with the actual `BracketReviewSequence`, preserving source, capture timestamp, optional capture-device/lens summary, optional capture-location policy summary, shot EVs, asset identifiers, file type, capture state, metadata state, RAW/processed availability, best-exposure markers, clipping warnings, and optional applied recipe metadata. The location summary records authorization, policy, and sample-presence facts only; it does not store precise coordinates. The app now produces manifests for deterministic simulated review and completed Photos-backed capture sequences, and `CameraController` stamps the active applied recipe record into both paths. Review chrome exposes manifest sharing as JSON separately from photo sharing, while `review.sequence.manifestRecipe` and `review.live.manifestRecipe` expose the active recipe snapshot for tests and future workflow handoffs.

## Observability

`CameraRuntimeDiagnostics` is the structured in-app diagnostics model. It records category, severity, title, detail, optional action path, optional duration, and timestamp. The camera exposes hidden accessibility probes for summary/latest/export values, debug builds expose a Settings/About ShareLink, and review/histogram paths publish their own hidden timing probes. This keeps normal shooting UI clean while preserving inspectable simulator and device evidence.

## Verification

The test suite intentionally prefers pure tests for planning, settings, device capabilities, review, and analysis. UI tests use deterministic launch arguments for camera chrome, denied capability states, simulated capture/review, review fixtures, histogram, zebras, and focus peaking. Physical camera behavior remains a separate proof category because the simulator cannot validate sensor, Photos-library, or real-lens behavior.

The runbook layer gives that split copy-pasteable evidence paths. Simulator and unit runs should write `.xcresult` bundles under `build/`, then use `xcrun xcresulttool get test-results summary` and `xcrun xcresulttool get test-results metrics` to extract pass/fail and benchmark evidence. Physical-device lab runs should target `platform=iOS,id=<DEVICE-UDID>` and write `build/Bracketer-physical-device-lab.xcresult`; the bundle is only an evidence container until real camera, Photos, Files, Shortcuts, Spotlight, and Foundation Models artifacts are attached.

Per-scenario runbooks use `build/physical-lab/Bracketer-<scenario-id>-physical.xcresult` and `BracketerPhysicalResultBundleIndex.Entry` records so a future real-iPhone run can map a bundle to a scenario without introducing private asset identifiers or raw media into app storage.

The unit contract gates the production catalog factory, runbook/result-bundle-index schema versions, canonical physical-proof ids, recorded-proof privacy shape, and duplicate rerun indexing so the lab handoff cannot silently drift while still reporting zero physical proof.

The ingestor contract adds a second gate: a future real-device submission must carry a physical `platform=iOS,id=<DEVICE-UDID>` destination string, a scenario-bound result-bundle filename and SHA-256 digest, result-bundle summary SHA-256 digest, typed result-bundle summary status/title/count metadata reconciled against result-bundle metrics, a scenario-bound result-bundle test contract with xcodebuild and xcresulttool versions, result-bundle timing metadata that places capturedAt inside the scenario test window, result-bundle device/platform metadata proving a physical iOS platform with an OS version or build label matching the submitted iOS build, a manifest snapshot SHA-256 digest, a fresh capturedAt timestamp echoed in reviewer evidence, all scenario-expected artifact ids, an `iPhoneN,M` device model identifier, hashed device identifier, dotted iOS version or Apple build number, and scenario-bound reviewer evidence containing the selected runbook's evidence descriptors, typed result-bundle summary tokens, summary digest, metric-prefixed counts/duration/attachment bytes, test-contract tokens, timing tokens, and result-bundle device tokens before Bracketer can replace the scenario's recorded proof entry.
